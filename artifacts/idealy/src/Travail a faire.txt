Voici les spécifications techniques et fonctionnelles à implémenter :

1. L'Écran de Sélection initial (Onboarding à 3 Cartes)
Au moment où l'utilisateur termine son inscription, il ne doit pas tomber sur un tableau de bord vide. On doit lui présenter une interface de choix basée sur 3 cartes interactives :

La Voie du Ninja

La Voie du Mage

La Voie du Hunter

L'utilisateur clique sur l'une des cartes pour définir l'univers de son projet, puis clique sur "Suivant".

2. Génération Dynamique du Lore et Nom des Agents
Selon la carte choisie, tout le jargon technique de l'application (et les rôles des agents IA en arrière-plan) doit se transformer dynamiquement pour correspondre à l'univers choisi.

Exemple si l'utilisateur choisit "Ninja" : L'agent IA responsable de la structure ou de l'architecture ne doit pas s'appeler "AI Architect", mais prendre un nom comme Shika-Architect ou Shikamaru. Si c'était la voie "Mage", cet agent pourrait s'appeler Luxus-Dev.

3. Fonctionnalités Immersives (Exemple de la Recherche)
Je veux que les actions de l'application soient scénarisées.

Mécanique de recherche : Si l'utilisateur demande à INIA de chercher et d'analyser les fonctionnalités d'une autre application existante (comme Shopify) pour s'en inspirer, l'interface ne doit pas juste afficher un loader "Recherche en cours...".

À la place, on doit afficher de manière immersive que l'application "envoie l'Équipe 7 (ou l'Équipe de Natsu / l'équipe de Kirua selon l'univers) en mission de détection" pour récolter les informations et revenir avec le rapport.

Objectif final

À la fin du développement, Idealy doit donner l'impression d'être un produit créé par une équipe de plusieurs centaines d'ingénieurs, avec un niveau de finition comparable aux meilleurs SaaS mondiaux. Chaque interaction doit être fluide, chaque détail cohérent, et l'expérience suffisamment marquante pour que les utilisateurs aient envie de revenir autant pour l'ambiance que pour la qualité de génération.
Tu dois modifier la stratégie technique d’Idealy avant de poursuivre son développement.

Idealy ne doit plus être construit comme une application dépendant exclusivement de Next.js. Nous voulons une architecture plus libre, modulaire et capable de profiter des meilleurs avantages de plusieurs écosystèmes modernes.

Cette modification concerne deux éléments différents :

les technologies utilisées pour construire Idealy lui-même ;
les technologies vers lesquelles Idealy pourra générer et exporter les applications de ses utilisateurs.

Ne confonds jamais ces deux parties.

1. OBJECTIF GÉNÉRAL

Construire Idealy comme un studio de développement IA moderne, rapide, modulaire et indépendant d’un framework unique.

La technologie principale doit rester stable et cohérente. Il ne faut pas mélanger React, Vue, Nuxt et Svelte dans les mêmes pages sans raison.

Nous voulons plutôt :

utiliser React pour le cœur de l’application ;
utiliser Vite pour le développement et la compilation ;
utiliser React Router pour la navigation et l’architecture applicative ;
reprendre les meilleures pratiques de Vue, Nuxt et Svelte ;
isoler certains modules spécialisés lorsqu’une autre technologie apporte un réel avantage ;
préparer un moteur d’export universel capable de produire plusieurs frameworks.

React permet de construire l’interface à partir de composants, tandis que Vite fournit un environnement de développement et de compilation rapide. React Router peut gérer la navigation et les flux applicatifs sans imposer Next.js.

PARTIE A — TECHNOLOGIES UTILISÉES POUR CONSTRUIRE IDEALY
2. FRONTEND PRINCIPAL

Utilise comme base principale :

React ;
TypeScript ;
Vite ;
React Router ;
Tailwind CSS ;
shadcn/ui ou une bibliothèque interne dérivée ;
Framer Motion ou Motion pour React ;
Zustand pour l’état local global ;
TanStack Query pour les données asynchrones ;
Monaco Editor pour le code ;
Web Workers pour les tâches lourdes côté navigateur.

Le frontend principal d’Idealy doit rester en React.

Ne reconstruis pas certaines pages en Vue ou en Svelte simplement pour utiliser plusieurs technologies. Cela rendrait l’application plus lourde et difficile à maintenir.

L’objectif est d’exploiter plusieurs idées technologiques, pas de créer un mélange désorganisé.

3. POURQUOI NE PAS UTILISER NEXT.JS COMME CŒUR

Ne fais plus de Next.js une dépendance centrale.

Idealy doit pouvoir être déployé sur :

Vercel ;
Netlify ;
Cloudflare Pages ;
un hébergement statique ;
une infrastructure personnalisée.

Utilise une architecture frontend découplée des services backend.

Les fonctionnalités qui étaient autrefois liées à Next.js doivent être remplacées par des modules indépendants :

React Router pour la navigation ;
Vite pour le build ;
API serverless ou services externes pour le backend ;
Supabase pour l’authentification et les données ;
fonctions serverless uniquement lorsqu’elles sont nécessaires.

Ne supprime pas une fonctionnalité existante simplement parce qu’elle venait de Next.js. Remplace son implémentation sans casser son comportement.

4. CE QU’IL FAUT PRENDRE DE VUE ET NUXT

Vue et Nuxt ne seront pas le frontend principal d’Idealy.

Ils doivent servir de références pour améliorer l’architecture et l’expérience de développement.

Reprends notamment :

la simplicité des composants ;
la séparation claire entre logique et présentation ;
les composables réutilisables ;
l’auto-organisation des fonctionnalités ;
les conventions de fichiers faciles à comprendre ;
une gestion lisible des états de chargement, d’erreur et de succès.

Nuxt est un framework full-stack basé sur Vue qui fournit notamment routage par fichiers, auto-imports et rendu côté serveur. Nous voulons nous inspirer de cette expérience développeur, sans reconstruire Idealy en Nuxt.

Organise donc React avec une structure aussi intuitive qu’un projet Nuxt :

src/
├── app/
├── routes/
├── features/
├── components/
├── layouts/
├── hooks/
├── services/
├── stores/
├── agents/
├── workflows/
├── integrations/
├── preview/
├── exporters/
├── themes/
├── lib/
└── types/
5. CE QU’IL FAUT PRENDRE DE SVELTE ET SVELTEKIT

Svelte ne doit pas remplacer React dans le cœur d’Idealy.

Utilise plutôt ses principes pour atteindre une interface plus légère et plus vivante :

transitions naturelles ;
peu de re-rendus inutiles ;
états locaux simples ;
animations liées directement aux changements d’état ;
composants courts et lisibles ;
réduction du JavaScript exécuté inutilement ;
interface extrêmement réactive.

SvelteKit est conçu pour créer des applications web robustes et performantes avec Svelte. Il constitue une bonne référence pour la fluidité et la simplicité, mais pas une raison de mélanger deux frameworks dans le même écran.

Reproduis cette sensation dans React avec :

Motion pour React ;
CSS Transitions ;
CSS View Transitions lorsque disponibles ;
lazy loading ;
code splitting ;
memoization uniquement lorsqu’elle est utile ;
Web Workers pour les traitements lourds ;
rendu progressif des previews.
6. ANIMATIONS ET INTERACTIONS

Le système d’animation doit être centralisé.

Crée des tokens de mouvement :

export const motionTokens = {
  duration: {
    instant: 120,
    fast: 180,
    normal: 260,
    slow: 420,
  },
  easing: {
    standard: [0.22, 1, 0.36, 1],
    enter: [0.16, 1, 0.3, 1],
    exit: [0.7, 0, 0.84, 0],
  },
};

Utilise les animations pour :

ouvrir et fermer la sidebar ;
faire apparaître la preview ;
transformer l’écran d’accueil en espace de travail ;
afficher les réponses des agents ;
montrer la construction progressive d’une application ;
déplacer et redimensionner les panneaux ;
animer les changements de thème ;
afficher les états de réussite ou d’erreur ;
réagir à la saisie dans le champ de prompt.

Les animations doivent être fluides, sobres et utiles.

Respecte prefers-reduced-motion.

Ne crée jamais d’animation qui bloque une action.

7. BACKEND ET DONNÉES

Le frontend ne doit pas contenir de secrets d’API.

Utilise une couche backend modulaire pouvant être remplacée.

Pour le MVP, privilégie :

Supabase Auth ;
Supabase PostgreSQL ;
Supabase Storage ;
Supabase Realtime ;
Edge Functions uniquement quand elles sont indispensables.

Crée des interfaces abstraites :

interface AuthProvider {}
interface DatabaseProvider {}
interface StorageProvider {}
interface AIProvider {}
interface DeploymentProvider {}

Le reste de l’application ne doit pas dépendre directement de Supabase.

Cela permettra plus tard de remplacer un service sans reconstruire toute l’application.

8. MODE SANS SERVEUR PERMANENT

Idealy doit fonctionner avec le moins d’infrastructure possible.

Utilise :

le navigateur pour l’interface ;
IndexedDB pour les brouillons locaux ;
Web Workers pour les traitements locaux ;
WebContainers ou une sandbox équivalente lorsque possible ;
services serverless pour les opérations sécurisées ;
fournisseurs gratuits ou clés personnelles des utilisateurs pour les modèles IA.

« Sans serveur » ne veut pas dire mettre les clés secrètes dans le navigateur.

Toute opération nécessitant un secret doit passer par :

une fonction serverless ;
une fonction Edge ;
ou une clé fournie directement par l’utilisateur et stockée de manière sécurisée.
9. ARCHITECTURE MULTI-AGENTS

Le système multi-agents doit être indépendant du frontend.

Structure recommandée :

User request
    ↓
Intent analyzer
    ↓
Mission planner
    ↓
Model router
    ↓
Specialized agents
    ↓
Validator
    ↓
Universal project model
    ↓
Preview renderer / Exporters

Chaque agent doit recevoir :

une mission précise ;
un contexte limité ;
les fichiers nécessaires ;
un budget de calcul ;
un résultat structuré attendu.

Ne laisse pas tous les agents modifier directement tout le projet.

Utilise un orchestrateur central qui :

attribue les tâches ;
fusionne les résultats ;
détecte les conflits ;
demande une correction ;
choisit automatiquement le modèle approprié ;
masque entièrement le nom des modèles à l’utilisateur.
PARTIE B — FORMAT UNIVERSEL D’IDEALY
10. NE PAS GÉNÉRER DIRECTEMENT UN FRAMEWORK

Le cœur d’Idealy ne doit pas être React, Vue, Nuxt ou Svelte.

Avant de produire du code, Idealy doit générer un modèle universel du projet.

Nom interne suggéré :

Idealy Universal Project Schema — IUPS

Ce schéma doit décrire :

les pages ;
les routes ;
les composants ;
les propriétés ;
les états ;
les événements ;
la navigation ;
les données ;
les appels API ;
les permissions ;
les thèmes ;
les tokens de design ;
le responsive ;
les animations ;
l’accessibilité ;
les assets ;
les dépendances ;
les tests attendus.

Exemple simplifié :

{
  "project": {
    "name": "Nova Finance",
    "targets": ["web", "ios", "android"],
    "theme": {
      "colors": {},
      "typography": {},
      "spacing": {},
      "radius": {}
    },
    "routes": [],
    "screens": [],
    "components": [],
    "dataModels": [],
    "interactions": [],
    "animations": []
  }
}

Ce format est la seule source de vérité.

La preview et tous les exports doivent être générés à partir de ce schéma.

11. PREVIEW INTERNE

La preview principale peut être rendue avec React parce que le studio principal utilise React.

Cependant, elle ne doit jamais devenir la source de vérité.

Flux obligatoire :

Prompt
→ IUPS
→ React Preview Renderer

Et non :

Prompt
→ React code
→ tentative de conversion vers les autres frameworks

Quand l’utilisateur modifie visuellement un composant, la modification doit d’abord mettre à jour l’IUPS, puis la preview doit être recalculée.

PARTIE E — RÈGLES DE QUALITÉ
16. RÈGLES ABSOLUES
Ne mélange pas plusieurs frameworks dans un même écran.
Ne migre pas aveuglément tout le code.
Ne supprime aucune fonctionnalité utile sans remplacement.
Ne fais pas dépendre le moteur universel de React.
Ne stocke aucune clé secrète dans le frontend.
Ne présente jamais les noms des modèles IA à l’utilisateur.
Ne prétends pas qu’un export est fidèle sans tests visuels.
Ne génère pas de faux boutons ou de fonctionnalités non connectées.
Chaque action visible doit fonctionner.
Chaque panneau doit avoir ses états vide, chargement, succès et erreur.
Toutes les modifications importantes doivent être testées.
Conserve une application utilisable après chaque phase.
17. CRITÈRES DE VALIDATION

La migration est réussie lorsque :

Idealy fonctionne sans dépendre de Next.js comme runtime principal ;
l’accueil, le chat, l’onboarding et la preview fonctionnent ;
la sidebar est réellement rétractable ;
la preview reste cachée avant la première génération ;
les agents utilisent une orchestration indépendante de l’interface ;
un projet est représenté par l’IUPS ;
le même projet peut produire au minimum un export React, Vue, Nuxt et SvelteKit ;
les modifications du projet sont conservées entre les exports ;
le design reste cohérent ;
les thèmes clair, sombre et personnalisés fonctionnent ;
les erreurs sont visibles et récupérables ;
aucun secret n’est exposé dans le navigateur.
18. INSTRUCTION FINALE

Commence par analyser le code existant.

Présente ensuite :

les dépendances actuelles ;
les éléments liés à Next.js ;
les fonctionnalités à conserver ;
le plan de migration ;
les risques ;
la nouvelle arborescence.

Après cette analyse, commence immédiatement la migration par petites étapes vérifiables.

Ne reconstruis pas toute l’application en une seule opération.

À la fin de chaque phase :

exécute le build ;
exécute les tests ;
corrige les erreurs ;
vérifie les interactions ;
documente les changements ;
puis passe à la phase suivante.

L’objectif final est de construire Idealy avec une base principale React + Vite + React Router, une expérience inspirée de la simplicité de Nuxt et de la fluidité de SvelteKit, puis de permettre l’export réel des projets vers React, Vue, Nuxt, Svelte, Next.js, Expo, Flutter, SwiftUI, Jetpack Compose et d’autres technologies à partir d’un modèle universel unique.
